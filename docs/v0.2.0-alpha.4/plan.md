# v0.2.0-alpha.4 设计与开发计划

更新：2026-10-28。**代码、Windows 原生完整回归、双端 CI 与公开发布核验已完成。** 当前源码及公开预发布 **0.2.0-alpha.4**。用户本轮明确授权修复相似问题、自行完成 Windows 与当前可行 Linux 测试、推送 dev、PR 合并 main 后同步 dev。提交、PR 与合并文案使用极简英文；真实系统安装的未测边界见文末。

## 目标与范围

1. 修复本机 `mpv_ambiguous` 误报，先恢复可靠的核心与配置目录检测。
2. 一次操作只做一次应用内确认，在同一个弹窗中展示准备、下载、安装和结果，消除连续确认及被弹窗遮挡的反馈。
3. Windows x64 与 Arch/CachyOS x86_64 / KDE Wayland 使用相同交互结构，保留各自的原生安装和系统授权。
4. 按 WinUI 3 / Fluent 原则使用 Mantine 标准 Modal、Progress、Loader、Button、Alert。**删除按钮背景进度，按钮恢复正常宽度与留白。** 产品和现有离线预览同步。

保留 GitHub Releases、Tauri 标准 manifest、官方 updater 下载验签、摘要校验和现有文件事务。不开新页面、不加新运行时依赖或通用任务框架、后台自动安装或旧 alpha 兼容层。不改播放器预设、MPV 来源、分发类型或许可。

## 已查明的问题

详情和复现输出见 [本机调查](evidence.md)。调查基于 dev / `0499a4a`，接手时工作区干净。

| 问题 | 已确认的事实 | alpha.4 处理 |
| --- | --- | --- |
| 本机误报多个 MPV | 注册表和默认候选指向同一文件；Rust 构造结果分别含 `MPV Player\\mpv.exe`、`MPV Player/mpv.exe`，原始 OsStr 比较不相等。Windows Path 比较及 canonicalize 均相等 | 在 Windows 路径选择函数中统一候选表示及去重；保留大小写处理、路径校验和真实多安装阻断 |
| 确认次数多 | 增强流程依次经过下载确认、核心确认（缺失时）、部署确认；保存入口还可继续弹配置确认 | 删除只确认下载的中间层；核心、增强、配置保存各自明确操作，不再隐式串接安装与保存 |
| 弹窗挡住反馈 | 普通任务的 `working` 在主页面，确认 Modal 执行时仍打开；组件进度则在播放器页。两者没有统一任务呈现 | 当前任务的进度、错误和结果全部留在同一个 Modal 内 |
| 应用更新交互复杂 | Arch 在更新 Modal 内先下载再点击安装；Windows/Arch 用按钮背景和多态 progressbar 表达运行状态 | 改为标准进度控件与普通按钮；准备和执行阶段明确区分，仅写入前确认一次 |
| 错误过于笼统 | 截图首层为“操作未完成”，真实原因仅在 JSON 详情；普通错误同时渲染在页面及 Modal | 首层显示具体失败原因及可行操作，技术详情折叠；任务错误只在当前任务位置展示 |
| 短确认弹窗出现空白色带 | “放弃未保存的配置”只有标题和按钮，操作区仍有 20px 顶部 margin；全局 Paper 背景影响 Modal 内容，而标题和底栏各用不同背景 | 短确认按内容自适应，统一标题/正文表面；卡片样式限定页面范围，移除多余空白及重复操作区规则 |

截图未包含原始点击入口，不能断言它发生在下载、安装前还是更新完成后；本轮复现的是检测函数的误判条件，修复后的隔离测试见文末交接，不把调查输出当修复验证。

## 弹窗设计

用户最新决定覆盖 alpha.3 的“只用按钮背景进度”：参考 [Resona 的设计讨论](codex://threads/01a18079-7bef-7401-b487-71befe47df20)和本轮截图，借鉴**同窗展示版本、更新内容、独立进度条、短状态及底部按钮**。不复制其无关功能，也不继承另一项目的实施或发布授权。

```text
更新 MpvKit
0.2.0-alpha.3 → 0.2.0-alpha.4

更新内容 / 必要的影响摘要
详细变更（可展开）

━━━━━━━━━━━━━━━━━━━━  42%
正在下载

                         [安装] [取消]
```

这是位置示意，不代表下载中可点击安装。按钮随阶段按下表变化；主要动作在左，取消/关闭在右。没有第二个覆盖其上的应用确认框。

### 一次确认的具体流程

**唯一确认放在完整预览生成后、真正写入之前。** 用户明确点击更新/安装入口后，直接在同一 Modal 中做只读准备；必要的下载、验签、解包及包事务查询也在这个阶段完成。准备结束后呈现具体影响，点击一次“安装 / 更新 / 保存”即执行；完成后不再询问确认。

这意味着下载可以发生在唯一安装确认之前：入口点击明确发起准备，准备只产生受控临时数据，不安装核心、覆盖配置或调用提权。自动启动检查仍只发现版本，**不因发现更新而自动下载**。此安排沿用现有增强和 Arch 的先准备后预览能力，避免在用户确认之后才发现需要额外依赖或覆盖文件。

| 阶段 | 弹窗内容与反馈 | 按钮与关闭行为 |
| --- | --- | --- |
| 准备 | 立即显示“正在准备”；随后显示实际下载、校验、解包或查询状态 | 不显示可执行的安装按钮；仅支持真实可取消的准备操作，不把关闭伪装成取消 |
| 待确认 | 短标题、目标/版本、一句影响摘要；手改冲突与必要依赖浮出，文件/包明细可展开 | 普通 Button：“安装 / 更新 / 保存”及“取消”；保持 Esc、焦点锁和回焦 |
| 下载（若仍有系统包下载）/执行 | 原位置显示进度和阶段；按钮不变成进度条 | 执行动作禁用，不能重复提交；系统包事务期间不提供取消或强制退出 |
| 成功 | “已安装 / 已更新 / 已保存”；Arch 应用更新为“已安装，重新打开后生效” | “关闭”；无需再确认，不伪称当前进程已切换新版本 |
| 失败/取消授权 | 就地显示具体原因，详情默认折叠；说明已经发生的变化 | “重试”只重建准备和预览，不直接重复写入；“关闭”返回原页面并保留草稿 |

准备阶段的用户取消要丢弃当前候选并拒绝迟到结果。已有组件下载取消能力继续复用；应用更新如接入可取消下载，应通过官方客户端能力和任务释放实现，不新增下载器。不能可靠取消的短准备阶段保持可见反馈并等待结束，不提供无效按钮。查询/下载保留有界超时；包管理器提交阶段不沿用下载超时或强杀。

### 文案与按钮

| 操作 | 短影响摘要示例 | 唯一确认按钮 |
| --- | --- | --- |
| 应用更新 | “更新到 0.2.0-alpha.4。安装时将关闭 MpvKit。”（Windows）；“更新到 0.2.0-alpha.4，需系统授权。”（Arch） | 安装 |
| 核心更新 | “通过 WinGet 更新 MPV。” / “通过 Pacman 更新 MPV，需系统授权。” | 更新 |
| 增强更新 | “更新 uosc、thumbfast 和字幕字体。”（按实际变更生成） | 更新 |
| 覆盖手改 | “将覆盖这些手改内容。”，紧邻实际差异及无历史备份提示 | 保存 |

标题、摘要不重复；不使用“执行初始化”“确认继续”等泛词。真实多安装显示“发现多个 MPV 安装位置”，详情列出候选路径供核对，不只显示通用失败。中文与英文同时设计。

按钮使用标准 Mantine Button 与公开 props，正常内边距、可读文字、合理最小尺寸并随内容增长；不设截字、强制窄宽或为百分比保留宽度。操作区固定在弹窗底部；窄窗允许换行或纵排，主内容独立滚动。常规弹窗约 560，复杂文件差异最多 720，视口边距至少 16；这是项目布局选择，不声称是 WinUI 强制像素值。

### 短确认弹窗

用户补充的退出确认截图也纳入本版，不能只优化应用更新弹窗。当前标题下只有操作区，其固定顶部 margin 显露出一段空背景；全局 `.mantine-Paper-root` 又作用于 Modal 的 Paper 内容，形成标题、空带、底栏三种底色。

退出确认采用“退出 MpvKit？”＋“未保存的配置将丢失。”＋“放弃并退出 / 取消”，高度随这段实际内容自适应，默认聚焦取消。标题与正文同一表面，底栏若有轻微分区只保留一次，不能夹一个无内容的色带。其他短确认沿用紧凑间距，不继承长日志/任务进度弹窗的高度和滚动占位。

通过 Modal 公开 Styles API 和 Mantine Group/Stack 管理间距，收敛重复 `.dialog-actions` 规则；页面卡片背景限定作用范围，不能全局改变所有 Paper 而意外影响弹层。只复用简单布局，不引入通用弹窗框架。修改共享规则后核对退出、核心、配置、维护及更新等实际调用方，并同步离线预览。

### 进度规则

- 一处独立进度区域：已知下载总量用 Mantine Progress 和实际百分比；未知总量及准备、校验、等待授权、安装用标准 Loader 和一行短阶段。未知时没有百分比，不能用 `value=100` 的条纹条冒充确定进度。
- 增强逐组件显示名称和该文件真实下载百分比，不虚构整个安装任务的加权总进度。下载 100% 后切换“正在校验 / 正在安装”，不显示“已完成”。
- WinGet/Pacman 当前没有可靠的结构化字节进度：显示“正在通过 WinGet 更新 / 等待系统授权或安装”，不解析本地化终端文字造百分比。只在后端确实知道阶段时细分授权与安装。
- 进度区域靠近底部操作区，在长日志、依赖列表与 640×600 下仍可见；不在遮挡后的主页面重复放第二套进度。切页、自动检查、失焦刷新不能盖掉当前任务 Modal。
- 确定进度提供可访问名称及 aria-valuenow；未知省略数值。仅阶段变化和结果用 live region，避免每个字节重复播报。尊重高对比与减少动态效果。

## 双端实现边界

| 对象 | Windows x64 | Arch / CachyOS x86_64 |
| --- | --- | --- |
| MPV 路径 | 修复注册表/默认候选分隔符去重；覆盖启动状态、配置根解析及核心预览/复核的共用调用点 | 保持固定 `/usr/bin/mpv` 和现有路径保护，无额外扫描 |
| 核心 | 固定 shinchiro.mpv / winget；查询预览后一次确认；执行期间 Modal 内未知进度 | 固定 pacman mpv；一次应用确认后由 pkexec 请求系统授权；修正现有核心执行超时与应用更新不强杀 Pacman 的边界差异；不刷新数据库或递归卸载 |
| 增强 | 同窗准备、下载、验签/解包、具体变更确认、现有文件事务执行 | 同一 UI 和业务语义，仍只部署 Linux 载荷 |
| 应用 | 扩展现有 prepare/install 分离：官方 updater 先下载验签，暂存当前候选载荷，确认后交回官方 NSIS 安装 | 复用 prepare_app_update 的下载验签、包元数据及 Pacman 事务预览，唯一确认后执行固定 pkexec/Pacman 参数 |
| 完成 | 安装器接手前显示“正在启动安装”；NSIS 显示自己的安装进度，不能声称应用关闭后还能在 WebView 持续显示 | 查询实际安装版本/归属后提示重开；保留进程中的旧版本事实 |

系统 UAC/Polkit 是操作系统授权，不计作第二个应用确认，也不能省略或仿制。Windows 官方 NSIS 交接/关闭行为和 Linux 授权代理实际窗口需要原生验证。

当前“安装并保存 / 修复并保存”会隐式串接多个任务。已收敛为：组件区负责核心与增强的独立安装/维护，底部负责配置预览与保存；缺必需组件时就地指出“请先安装 MPV / 播放增强”，保留草稿，不自动跳进另一轮安装确认。首次核心安装、增强安装、保存是用户明确选择的独立任务，各一次确认；不新增跨包管理器与文件事务的组合回滚框架。

单次操作的短状态留在现有 React 组件中，用有限的阶段值和当前候选标识表达。复用现有 Channel、Pending、锁、fingerprint、过期检查和恢复机制；复用已有事件并补准备/执行/完成呈现，不做可配置任务引擎。准备数据留在已有候选生命周期中，取消、换候选、错误和退出时释放；不增加历史缓存或手动清理入口。

路径修复在 Windows 平台模块完成：先按现有规则验证本地绝对路径及重解析点，再统一表示并去重；canonicalize 在本轮仅用于只读证明同一文件，不能用它绕过路径安全规则。真正两个安装仍拒绝，不擅自选一个、卸载或清理。所有写入前继续复核预览状态。

## 测试与验收

| 层次 | 需要验证的实际风险 | 环境及结果要求 |
| --- | --- | --- |
| Windows 路径回归 | `/` 与 `\\`、重复注册表视图、大小写/末尾分隔符、一个文件不误报；两个实际文件仍阻断；相对路径、重解析点不放行 | Windows Rust 单测；默认 cfg(test) 绕过真实注册表，需另做本机只读检测，不能只看现有 fixture 通过 |
| 确认次数与状态 | 核心、增强、应用、保存各只有一次执行确认；准备、首字节延迟、42%、未知总量、校验、执行、成功、错误可见 | 现有原生 WebView/IPC fixture 与离线预览；计数执行命令和确认次数，禁重复提交和迟到事件 |

| Windows 更新 | 官方下载验签、NSIS 交接、退出及重开后的版本/单实例 | 本机隔离根验证 IPC；真实跨版本 NSIS 安装仅在隔离用户/VM；没有环境则明确未测 |
| Linux 更新 | Rust、makepkg、包元数据/版本/归属、隔离载荷、签名；桌面授权、依赖拉取及跨版本重开 | 构建/包检查在可用 Arch 环境或 CI；真实 Polkit/KDE Wayland 与系统事务必须在隔离 VM 分别验收 |

实施后最小命令集沿用 [测试入口](../testing.md)：`pnpm build`、`pnpm test:frontend`、Rust fmt/test/clippy、Windows debug EXE 和 `pnpm test:e2e`、预览 build/check；修改更新/分发契约时运行 `node --test scripts/release.test.mjs`，Linux 执行相应 Rust、构建与包专项。纯样式/文案不新增镜像实现的测试；补确认计数和路径去重这两个有真实故障依据的回归。

当前 Windows 主机不具备可用 Linux 桌面环境。本版本开发应自行完成可行双端测试，但不能承诺用容器证明 Polkit、KDE Wayland 或重启体验，也不能用 mock 证明真实 NSIS 更新。未验收部分列清触发条件、影响与复验入口，不把历史 alpha.3 结果转写成本版通过。
